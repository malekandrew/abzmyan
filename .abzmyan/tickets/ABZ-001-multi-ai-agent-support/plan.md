# Implementation Plan: ABZ-001

## Summary
Today, `init` and `update` hardcode a single destination (`.claude/commands/`) for abzmyan's six agent command files. This ticket makes that destination a set: `init` gains a multi-select prompt for which AI coding agent(s) the user works in (Claude Code, Cursor, GitHub Copilot, OpenAI Codex CLI, Gemini CLI), persists that selection to `.abzmyan/config.yml`, and writes the six command templates into each selected tool's native custom-command directory in that tool's native format. `update` grows the same capability retroactively: it refreshes command files for every currently-configured agent, and offers a way to add/change the selection later. The four new tools each require a different directory and, in two cases (GitHub Copilot, Gemini CLI), a different file format (added frontmatter, or a TOML wrapper) — not just a copy to a new path. One tool, OpenAI Codex CLI, has no clean native equivalent of "explicit slash command with an argument that a human triggers once per ticket," which is flagged below as an open question rather than silently resolved.

## Files to create/modify
- `src/agents.js` — **new**. Central registry of the 5 supported agents: id, display label (for the prompt choices), the project-relative commands directory, the output filename for a given command base name, and a `render(commandName, rawMarkdownContent)` function that produces that agent's native file content (verbatim passthrough for Claude Code/Cursor, frontmatter-wrapped for GitHub Copilot's custom agents, TOML-wrapped for Gemini CLI). Also holds the one-line descriptions for the 6 commands (needed by GitHub Copilot's and Gemini's optional frontmatter/description fields) and the `DEFAULT_AGENTS = ['claude-code']` fallback used for pre-ticket projects.
- `src/scaffold.js` — generalize `copyCommandTemplates(projectRoot)` into `copyCommandTemplates(projectRoot, agentIds)`: for each agent in `agentIds`, ensure its commands directory exists, run every template through that agent's `render()`, and write it under that agent's filename convention. Return a per-`{agentId, file, change}` summary instead of a flat filename list, so callers can report per-agent. Add `readAgentsFromConfig(projectRoot)` (returns the configured agent id list, defaulting to `['claude-code']` if `config.yml` has no `agents:` key at all) and extend `writeConfig` to also render an `{{AGENTS_BLOCK}}` token. Both new read/patch operations on `config.yml` go through the new `yaml` dependency (see below) rather than hand-parsing.
- `templates/config.yml.template` — add an `agents:` block (rendered as a YAML list) after `abzmyan_version`, via a new `{{AGENTS_BLOCK}}` placeholder, following the same string-substitution pattern already used for `{{DEPLOY_BLOCK}}`.
- `src/commands/init.js` — add a `multiselect` prompt (via the existing `prompts` dependency) listing the 5 agents in the order given in the requirements, `min: 1`, nothing pre-selected by default (consistent with the ticket's explicit-choice-only stance — no auto-detection). Pass the selected agent ids through to `writeConfig` (for the `agents:` block) and to the generalized `copyCommandTemplates(projectRoot, selectedAgentIds)`.
- `src/commands/update.js` — read the current agent selection via `readAgentsFromConfig`; refresh command files for every currently-configured agent (generalizing today's Claude-Code-only refresh loop, with the added/updated/unchanged report now grouped or prefixed by agent so multi-directory output stays readable); then run a second `multiselect` prompt ("Add or change AI agents for this project?"), pre-populated (`selected: true`) with the currently-configured agents; if the confirmed set differs from what was read, write command files for any newly-added agents and rewrite `config.yml`'s `agents:` list via a new `writeAgentsToConfig(projectRoot, agentIds)` helper in `scaffold.js`. If the set is unchanged, don't touch `config.yml`.
- `package.json` — add the `yaml` runtime dependency (justification below); update `description` to mention the newly supported agents; update `keywords` to add entries for the new tools (e.g. `cursor`, `github-copilot`, `codex-cli`, `gemini-cli`) alongside the existing `claude-code`.
- `README.md` — update the "Install" section's scaffolded file-tree example to show the per-agent command directories (conditioned on selection, or shown as "one of" per agent), mention the multi-select prompt as part of what `init` asks; update the workflow intro paragraph and any other spot that reads as Claude-Code-exclusive (the intro currently says "a lightweight, spec-driven-development workflow for Claude Code" — reword to name all 5 supported agents or speak generically about "your AI coding agent(s)"); note that `update` can also change the agent selection.

## Step-by-step approach
1. Add the `yaml` dependency to `package.json` and install it.
2. Write `src/agents.js`: the 5-entry registry described above, plus the shared command-description lookup table (one line per command, reusing wording already established in `.abzmyan/index/api-index.md`'s command table) and per-agent `render()` implementations:
   - `claude-code`, `cursor`: passthrough (identical markdown, different directory: `.claude/commands/<name>.md` vs `.cursor/commands/<name>.md`).
   - `github-copilot`: `.github/agents/<name>.agent.md` — **custom agents** (VS Code Copilot Chat's current name for what was `.chatmode.md`/"custom chat modes"), not prompt files. Prepend a minimal YAML frontmatter block (`description: <one-liner>`) to the unmodified markdown body; deliberately omit the optional `tools`/`model`/`handoffs` fields — `handoffs` in particular defines automatic agent-to-agent transitions, which would encode auto-chaining and conflicts with abzmyan's "no orchestration/auto-chaining, by design" principle (`.abzmyan/index/architecture.md`). Custom agents are invoked by **selecting the agent from the chat mode dropdown, then typing a message directly** (no `/name` slash command, no way to pass an argument at selection time) — a closer functional match to abzmyan's "invoke this agent, then give it a ticket ID/idea" pattern than prompt files' slash-command style, since the file body is simply prepended to whatever the user types next.
   - `gemini-cli`: `.gemini/commands/<name>.toml` — emit `description = "<one-liner>"` and `prompt = '''<unmodified markdown body>'''` (TOML literal multi-line string, so no escaping of the markdown's backticks/`$`/quotes is needed). Confirmed via Gemini CLI's docs that when a command's `prompt` has no `{{args}}` placeholder, the CLI appends whatever trailing text the user typed after the prompt automatically — so no content change is needed to preserve the "pass a ticket ID as an argument" behavior.
   - `codex-cli`: implement per whichever option is chosen in the open question below, once resolved.
3. Update `templates/config.yml.template` to add the `agents:` / `{{AGENTS_BLOCK}}` section.
4. In `src/scaffold.js`: generalize `copyCommandTemplates`, add `{{AGENTS_BLOCK}}` rendering to `writeConfig`, and add `readAgentsFromConfig` / `writeAgentsToConfig` built on `yaml.parse` / `yaml.stringify`.
5. Update `src/commands/init.js` to add the multiselect prompt and thread the selection through.
6. Update `src/commands/update.js` to read the current selection, refresh all configured agents' files, then run the add/change-agents prompt and apply any change.
7. Update `package.json` `description` and `keywords`.
8. Update `README.md`.
9. Manually smoke-test: run `npx abzmyan init` in a scratch directory selecting a mix of agents (including all 5) and confirm each tool's directory/file/format comes out as designed; run `npx abzmyan update` against an old-style `config.yml` (no `agents:` key, simulating a pre-ticket project) and confirm it defaults to Claude-Code-only, still refreshes `.claude/commands/`, and the add-agents prompt works; run `update` again after adding an agent and confirm `config.yml` and the new directory are both updated.

## New dependencies
- **`yaml`** (pure-JS, no transitive dependencies) — `config.yml` currently only ever gets written (via string-template substitution), never read back into the program. This ticket requires `update` to read an existing, possibly hand-edited, `config.yml` to discover the current agent selection and to detect the pre-ticket case (no `agents:` key), then rewrite it after a change. Hand-rolling a parser for this is exactly the kind of fragile, ad-hoc YAML handling (comments, indentation, list syntax) the project's existing "no templating engine, just `.replace()`" convention was fine avoiding when the file was write-only — now that it needs a real read-modify-write round trip, a small standard library is more robust than regex parsing. `writeConfig`'s existing string-substitution style for the *initial* render (during `init`) is left as-is to minimize churn; `yaml` is used specifically for `update`'s read/patch path.

## Edge cases considered
- **Pre-ticket projects** (`config.yml` has no `agents:` key): `readAgentsFromConfig` returns `['claude-code']`, `update` still refreshes `.claude/commands/` exactly as before and doesn't touch/break it, and the add-agents prompt is offered with only Claude Code pre-selected — matches the AC verbatim.
- **Deselecting an agent in `update`'s add/change prompt**: the AC only specifies behavior for *adding* agents ("writes command files for any newly-added agents"). To avoid unrequested destructive behavior, removing an agent from the selection updates `config.yml`'s `agents:` list (so `update` stops refreshing that agent's files going forward) but does **not** delete that agent's already-written command directory/files. This is a deliberate, conservative scope choice, not a gap — flag if the user wants deletion-on-removal instead.
- **GitHub Copilot / Gemini CLI frontmatter injection**: verified none of the 6 existing command templates contain sequences that would break simple frontmatter prepending (no leading `---` in the body) or TOML literal-string wrapping (no `'''` sequence in any template) — so both transforms are safe as designed today, but the check is worth re-running if command content changes later.
- **GitHub Copilot custom agents have no equivalent of a slash-command argument**: the existing command bodies illustrate their argument with Claude-Code-flavored examples (e.g. architect.md's "Parse the ticket ID from the command argument (e.g. `/architect XTG-003`)"). Copied verbatim into a `.agent.md` file, that example is cosmetically slightly off (there's no `/architect` to type — the user just selects the agent from the dropdown and types `XTG-003` directly) but still functionally clear to a model reading its own instructions. Per this ticket's explicit scope ("not what they say"), the command bodies are copied unmodified — flagging this as a known, accepted cosmetic mismatch rather than a reason to special-case content per agent.
- **Cross-project collisions if Codex CLI ends up using its (deprecated) user-global `~/.codex/prompts/` directory**: every abzmyan project would write identically-named commands (`architect`, `builder`, etc.) into the same shared, non-project-scoped directory, so multiple abzmyan-managed projects on one machine would clobber each other's Codex prompts. This reinforces the recommendation in the open question below.
- **`update`'s console output** needs restructuring since there can now be multiple destination directories per run — group the added/updated/unchanged report by agent so it doesn't read as one flat, ambiguous list the way it does today.
- **Existing Claude-Code-only behavior**: `copyCommandTemplates`'s Claude Code branch produces byte-identical output to today's implementation (same directory, same filenames, same content) — confirmed no unrequested changes to that path.

## Definition of done
- `npx abzmyan init` presents a multi-select (Claude Code, Cursor, GitHub Copilot, OpenAI Codex CLI, Gemini CLI), refuses to proceed with zero selected, and writes all 6 command files into each selected tool's native directory/format as designed above.
- The selection is persisted in `.abzmyan/config.yml` under a new `agents:` list.
- `npx abzmyan update` refreshes command files for every currently-configured agent, matching current template content, exactly as it does today for `.claude/commands/`.
- `npx abzmyan update` offers a pre-populated multi-select to add/change agents; confirming a changed set writes files for newly-added agents and updates `config.yml`.
- `update` on a pre-ticket project (no `agents:` in `config.yml`) defaults to Claude-Code-only, still offers the selection prompt, and does not remove or break `.claude/commands/`.
- Only the 5 named tools are offered — no generic fallback folder.
- `README.md`'s install/workflow sections and file-tree example reflect per-agent command directories; no remaining wording implies Claude-Code exclusivity.
- `package.json` `description` and `keywords` mention the newly supported agents.
- No other template/doc wording in this repo (checked: `templates/commands/*.md`, `templates/index/*.md`) implies Claude-Code exclusivity — confirmed clean already, no changes needed there.
- Selecting only Claude Code during `init` produces identical output (files, locations, content, workflow) to today's behavior.

## Open questions / risks
- **OpenAI Codex CLI has no clean native equivalent of the other four tools' "explicit `/command <ticket-id>`, human-triggered once per invocation" model**, and the two candidate mechanisms each have a real downside — this needs a human decision before Builder implements the `codex-cli` entry in `src/agents.js`:
  - **Custom prompts** (`~/.codex/prompts/<name>.md`, supports `$1`/`$ARGUMENTS`-style explicit argument passing — the closest behavioral match to Claude Code/Cursor) — but OpenAI's own docs mark this mechanism **deprecated** in favor of skills, and critically it is **stored under the user's home directory, not the project**, so it can't be committed to the repo, can't be "kept in sync" per-project the way every other agent's files are, and collides across different abzmyan projects on the same machine (see Edge cases above).
  - **Skills** (`.codex/skills/<name>/SKILL.md`) — the current, non-deprecated, project-scoped mechanism (lives in the repo, git-shareable, matches how every other tool in this ticket is being wired up) — but skills **activate implicitly/automatically when Codex judges them relevant**, not via an explicit slash command a human types with a ticket-ID argument. This is a meaningfully different (and less predictable) trigger model than abzmyan's precondition-gated, one-stage-at-a-time design relies on for every other tool.
  - **Recommendation:** default to Skills, since it's the only project-scoped, non-deprecated option and keeps the "files live in the repo, `update` keeps them in sync" property consistent across all 5 tools — but flag to the user that this changes *how* a human invokes each stage in Codex CLI specifically (relying on Codex's relevance-detection rather than an explicit command), and get explicit confirmation before Builder implements it. If the user instead prefers exact invocation-model parity with the other 4 tools, the deprecated custom-prompts path is the fallback, accepting its non-project-scoped storage and deprecation risk.
- **GitHub Copilot's custom-agent mechanism (`.github/agents/*.agent.md`, confirmed with the user as matching their own experience: select the agent from the chat mode dropdown, then type directly) is a VS Code Copilot Chat feature — not the standalone `copilot` CLI product**, which as of this writing has an open feature request (not yet shipped) for reading project-level custom commands/prompts at all. This plan targets the IDE-integrated mechanism as "GitHub Copilot['s] native custom-command/prompt directory," which matches the ticket's naming and the user's confirmed usage pattern, but is worth surfacing in case some readers of this plan use the standalone CLI tool instead.
